# בדיקות דפדפן (E2E)

הבדיקות פותחות את האתר בדפדפן אמיתי (Chromium דרך Playwright) מול מסד נתונים מקומי של Supabase, ועוברות את המסלולים העיקריים כמו שמשתמש עובר אותם. הן משלימות את בדיקות היחידה ואת בדיקות ה-RLS, ולא מחליפות אותן.

## מה נבדק

| קובץ | המסלול |
|---|---|
| `e2e/tests/access-test.ts` | עובד חדש נכנס בקישור לדוא"ל (המייל נלכד ב-Mailpit), ממלא בקשת גישה, מנהלת המערכת מאשרת, והעובד רואה את דף הבית. |
| `e2e/tests/supplier-test.ts` | עורך מחפש ספק מדף הבית, פותח את דף הספק, רואה את פס "מותר / לא מותר / לבדוק" ומוסיף טלפון. |
| `e2e/tests/approach-test.ts` | עורך פותח בקשת התקשרות, בודק מסלול, רושם פנייה דרך האזור האישי; הספק מגיש הצעה באזור האישי; העורך רואה "הגיש הצעה", והסכום נשאר חתום עד המועד. |
| `e2e/smoke/site-test.ts` | אחרי כל פרסום של האתר (deploy-web): האתר המפורסם נפתח בלי שגיאות ומציג את הכניסה. |

## בדיקת המסכים (נוספה 25.11.2026)

`e2e/screens/screens-test.ts` פותח את המסכים העיקריים פעמיים: בגודל טלפון (Pixel 7) ובגודל מחשב (1280 על 800). המסכים: בית, איתור ספקים, הוספת ספק, מזהים ממתינים (סגור ופתוח), ניהול, בקשות התקשרות, וחלון עריכת ספק. בכל מסך נבדק:

- **אין גלילה לרוחב**: הדף לא רחב מהמסך, אז שום דבר לא נחתך בצד.
- **אין כפתור "שומר…" בלי לחיצה**.
- **נגישות לפי axe**: לכל כפתור ולכל קישור יש שם, לכל שדה יש תווית, והניגודיות של הצבעים מספיקה (WCAG 2.2 AA).
- **השוואה לצילום המאושר**: צילום המסך צריך להיות זהה לצילום שב-`e2e/screens/baseline/` (סובלנות של 1% לפיקסלים, בגלל הבדלים קטנים בהחלקת הגופן בין מחשבים).

הבדיקות האלה רצות לפני המסלולים, כי המסלולים מוסיפים נתונים שהיו משנים את הצילומים. ב-CI הן חלק ממשימת `e2e`, ולכן שינוי מראה שלא אושר חוסם את המיזוג.

### כששינוי המראה מכוון

1. מאפסים את המסד המקומי (`npx supabase db reset`), כי המסלולים מוסיפים נתונים שמשנים את הצילומים.
2. מריצים `npm run e2e:screens:update`. הפקודה מצלמת בתוך הקונטיינר הרשמי של Playwright (`scripts/e2e-screens-docker.sh`, צריך Docker), שמצייר טקסט בדיוק כמו המחשב של GitHub. צילום ממחשב אחר שונה בכמה אחוזים מהפיקסלים בגלל החלקת הגופן, והבדיקה ב-CI הייתה נכשלת.
3. מסתכלים על הצילומים החדשים ב-`e2e/screens/baseline/` לפני ה-commit.
4. הצילומים נכנסים ל-PR, ו-GitHub מציג אותם לפני ואחרי. המיזוג הוא האישור.

כשהבדיקה נכשלת ב-CI, ה-artifact `e2e-report` מכיל את הצילום המאושר, הצילום החדש ותמונת ההבדלים.

## החשבונות

`e2e/seed.sql` מוסיף על נתוני הדמה (`supabase/seed/dummy.sql`) מנהלת מערכת, עורך ביחידה "אגף בדיקות א", ספקית שמשויכת ל"עמותת דמה לייעוץ", ושני מועמדי מזהה (שם קצר ושם ארוך) לבדיקת המסכים. הכתובות בדומיין `e2e.test`, והסיסמה המשותפת קיימת רק במסד המקומי. הקובץ לא רץ אף פעם על staging או על production.

בבדיקות שאינן בודקות את הכניסה עצמה, הכניסה נעשית בסיסמה מול המסד המקומי, והאסימון נשמר בדפדפן בדיוק כמו אחרי קישור כניסה. הכניסה בקישור עצמה נבדקת ב-`access-test.ts`.

## הרצה מקומית

1. `npx supabase start` (צריך Docker).
2. מעבירים לבדיקות את הכתובות מתוך `npx supabase status -o env`, עם הקידומת `E2E_`:
   `E2E_API_URL`, `E2E_PUBLISHABLE_KEY`, `E2E_DB_URL`, `E2E_MAILPIT_URL`.
3. `npm run e2e`. הבדיקות בונות את האתר מול המסד המקומי לתיקייה `e2e-dist` ומגישות אותו בכתובת `http://127.0.0.1:5173`.

אפשר להריץ את המסלולים שוב בלי לאפס את המסד (בדיקת המסכים צריכה מסד מאופס, ראו למעלה): כל ריצה יוצרת עובד חדש ונושא בקשה חדש. `psql` צריך להיות מותקן.

## ב-CI

- `tests.yml`, משימת `e2e`: מרימה Supabase מקומי עם המיגרציות, נתוני הדמה ופונקציות ה-Edge, ומריצה את `npm run e2e`. אם משהו נכשל, הדוח והעקבות (trace) נשמרים כ-artifact בשם `e2e-report` לשבוע.
- `deploy-web.yml`, משימת `smoke`: אחרי הפרסום מריצה את `npm run e2e:smoke` מול הכתובת המפורסמת.

## כשמוסיפים מסלול

- בוחרים רכיבים לפי תפקיד ושם נגיש (`getByRole`, `getByLabel`), כמו שמשתמש ומקרא מסך רואים אותם, ולא לפי מחלקות CSS.
- נתון שהבדיקה יוצרת מקבל שם ייחודי (למשל עם השעה), כדי שריצה חוזרת לא תתנגש בקודמת.
- חשבון או נתון קבוע חדש נכנס ל-`e2e/seed.sql`, בערכים מומצאים בלבד.
